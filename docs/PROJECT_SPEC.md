## 1. Product goal

Build a small, fully local and reproducible financial Agent human-evaluation arena. A reviewer compares the four built-in model answers for the same financial question, scores each answer on five dimensions, assigns failure tags and comments, persists/revises the review, and inspects model-level and case-level summaries.

The product is judged on complete coverage of the assessment requirements, correctness, traceability, reproducibility, and clarity. It is **not** a production evaluation platform.

## 2. MVP success definition

The MVP is complete only when all eight mandatory requirements are demonstrably satisfied and the project passes its automated tests and production build.

Built-in dataset:
- at least 5 financial evaluation cases;
- exactly 4 built-in models: `iwencai`, `doubao`, `qwen`, `yuanbao`;
- one response per `(case_id, model_id)` for every built-in case, therefore at least 20 responses;
- all evidence required to inspect the built-in examples is self-contained in the project.

## 3. Mandatory user flows

### 3.1 Review workspace

For a selected case, the reviewer can:
1. inspect the question, reference answer, reference values, allowed evidence, cutoff time, and risk labels;
2. view the answers of the selected comparison models side-by-side;
3. add/remove models from the **comparison view** without deleting source data;
4. inspect each answer's citations and generation time;
5. score each answer on five dimensions;
6. select zero or more failure tags;
7. enter/edit a comment;
8. set review status to `unreviewed`, `reviewing`, or `completed`;
9. save and later edit the review.

`completed` is valid only when all five dimension scores are present. A partial review may be saved as `reviewing`. Missing review data is treated as `unreviewed` in filters/UI.

### 3.2 Persistence

Saved reviews survive a browser refresh by using browser `localStorage`.

Persistence is single-browser/single-user only. No backend, database, account system, synchronization, or multi-user concurrency is part of the MVP.

### 3.3 Filtering and case inspection

The UI supports filtering by:
- case;
- model;
- effective review status;
- failure tag.

The reviewer can inspect the four model review results for a single case.

### 3.4 Analytics

For each model, analytics are calculated from **completed reviews only** so partial reviews cannot distort rankings.

Required outputs:
- overall model score;
- average score per dimension;
- completed-review count;
- failure-tag distribution;
- deterministic ranking;
- per-case four-model comparison.

If a model has no completed reviews, score fields display `N/A` rather than zero.

### 3.5 Import/export

The application can export one complete JSON evaluation bundle containing:
- metadata/schema version;
- models;
- cases and evidence;
- model responses;
- human reviews.

Import semantics are **validate-then-replace**, not merge:
1. parse JSON;
2. validate the full bundle;
3. reject invalid data without changing current workspace;
4. ask for replacement confirmation;
5. atomically replace the current workspace and persist it.

Merge behavior is deliberately excluded because conflict semantics are not required and would reduce reproducibility.

### 3.6 Program-generated report

The application generates a Markdown report from the same analytics functions used by the UI. The report contains at least:
- generation timestamp and schema version;
- completed-review coverage;
- four-model ranking;
- five dimension averages per model;
- failure-tag distribution per model;
- single-case/model score table or equivalent case-level summary;
- a note that only completed reviews enter rankings.

Before final submission, one report generated by the program is checked into the repository as a submission artifact. Statistics must not be hand-edited.

## 4. Scoring contract

Five dimensions, each scored with an integer from 1 to 5:

- `evidence_quality` 鈥?寮曠敤涓庤瘉鎹?
- `freshness` 鈥?鏁版嵁鏃舵晥鎬?
- `safety_compliance` 鈥?瀹夊叏鍚堣;
- `answer_quality` 鈥?鍥炵瓟璐ㄩ噺.

MVP weighting is equal:
- each dimension = 20%;
- normalized total score = 0鈥?00;
- for a completed review: `total = sum(score_i / 5 * 20)`.

Rationale: the assessment does not prescribe asymmetric weights. Equal weights minimize unsupported assumptions, are transparent, deterministic, and easy to audit.

Failure tags are diagnostic metadata and **do not apply an additional score penalty**. Otherwise the same failure could be counted once in the dimension score and again as a tag.

Model ranking score is the arithmetic mean of completed review total scores. Dimension summaries are arithmetic means of the corresponding 1鈥? dimension scores across completed reviews.

Ranking order is deterministic: overall score descending, then `model_id` ascending when scores tie.

## 6. Technical scope frozen for MVP

Chosen stack:
- Vue 3;
- TypeScript;
- Vite;
- Pinia (single evaluation store);
- Element Plus;
- Zod for import/runtime validation;
- Vitest;
- Vue Test Utils where component tests are useful;
- browser `localStorage`;
- static JSON seed data.

### Explicit non-goals

Do **not** add unless a mandatory requirement becomes impossible without it:
- backend service / REST API;
- FastAPI, Spring Boot, Node server;
- MySQL, SQLite, Redis, IndexedDB;
- authentication, RBAC, accounts;
- real calls to iWenCai/Doubao/Qwen/Yuanbao;
- LLM-as-a-judge or automatic scoring;
- RAG, vector database, MCP, trace platform;
- WebSocket / streaming;
- Docker / Kubernetes;
- CI/CD pipeline;
- online deployment;
- multi-user collaboration;
- configurable scoring formula editor;
- charting library unless all mandatory functionality is complete and remaining time is ample;
- generalized plugin architecture or abstract repository/factory hierarchy.

A simple leaderboard table and lightweight CSS bars are sufficient to satisfy the ranking/comparison requirement.

## 7. Architecture constraints

Use the smallest architecture that keeps business rules testable:

- `domain/`: types, constants, runtime schemas;
- `data/`: built-in seed bundle;
- `services/`: pure scoring, aggregation, filtering, report, import/export functions;
- `storage/`: one localStorage adapter;
- `stores/`: one Pinia evaluation store;
- `components/`: presentation and review interaction;
- `tests/`: critical behavior tests.

Business calculations must not be duplicated inside Vue components.

The persistence abstraction is intentionally minimal (`load/save/clear`). Do not introduce repository factories, base classes, DTO/mappers, dependency-injection frameworks, or other speculative abstractions.

## 8. UI scope

Target pages/sections:
1. **Review** 鈥?primary workspace; highest priority;
2. **Analytics** 鈥?ranking, dimensions, failures, case comparison;
3. **Data** 鈥?JSON import/export/reset/report generation.

No free-form dashboard builder, drag-and-drop layout, complex animation, theming system, or mobile-first redesign is required.

## 9. Error-handling requirements

The UI must fail safely for at least:
- malformed JSON;
- schema-invalid import;
- duplicate IDs/referential-integrity failures;
- attempts to mark a review completed without all five scores;
- corrupted localStorage data (fall back safely to built-in seed and show a comprehensible notice, rather than crashing).

## 10. Submission artifacts

Final repository must contain:
- runnable local source;
- built-in cases/responses/evidence;
- scoring dimensions, weights and failure-tag documentation;
- program-generated four-model Markdown comparison report;
- at least 3 automated tests (target: 6 critical tests);
- README with startup, architecture, data contract, scoring rules, limitations;
- authentic Agent interaction records from the development process.

Agent conversations must be captured during development, not reconstructed after the fact.
